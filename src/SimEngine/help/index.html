The basic game loop

GameFactory.NewGame composes and initializes the session. Initialize() is idempotent. Update() advances the authored engine-time frame; Update(elapsedMicroseconds) asks the existing clock to accumulate elapsed host time into fixed simulation ticks. Neither gives the host permission to calculate gameplay.

Normal Update obeys Clock.CatchUpCap as a work budget, retaining excess earned ticks in Clock.PendingTicks. Update(0) drains that backlog without adding time. Clock.Alpha contains only the fractional next tick, never whole backlog. Pause retains earned work but accrues none; speed/rate changes affect future elapsed input. Terminal outcomes/faults cancel unapplied host time. Authoritative timestamps are now 64-bit throughout commands, lifecycle/state, work/retry, incident facts, saves/hash, snapshots/views and lockstep. Bounded per-Update counts are not session ages. Work definitions now retain exact GameDuration intent, resolved to long ticks against the selected session quantum without mutating shared definitions; WorkProgress retains long whole and Q32 fractional elapsed ticks in the existing work/production owners. Work views retain actual wide goals/progress. Production inspection gauges use normalized fractions, while unrepresentable scalar elapsed-work signals report a typed unavailable blocker. Scenarios require a time reference to time_definitions: positive rational quantum, explicit frame_ticks/ticks_per_second pacing, and optional calendar/horizon. GameSystem.GetSchedule(ISimulationTime) resolves once before Initialize; periodic durations must align exactly with the quantum. Calendars publish immutable named fields or null when absent. Physical work, movement, retry and network flow use that same session converter. Saved/hash declarations include time identity, quantum, horizon and captured schedules. Optional space and state references remain P3 work.

  • Command checkpoint → ordered engine systems → events/flush → each live entity.Update → tick completion.
  • Each capability contributes facts; only its entity settles the entity state.
  • Initialize and Update publish immutable GameSnapshot simulation data; Updated fires after publication.
  • There is no engine Draw phase, Drawn event, render model or RunFrame wrapper. Platform rendering is later.
  • RunTicks() is an explicit tools/test fast-forward path bypassing pace/pause, not normal player flow.
The target keeps the same lifecycle. It changes mandatory minute/calendar/tile assumptions inside the engine, not by moving time, pathfinding or completion logic into the host.

Every live entity has one settled state

Mobility, work, construction, process and incidents expose their actual facts through registered capability/state-source contracts. Authored state definitions supply priority and stable identity. Entity.Update resolves these in deterministic order and commits its state/state-age once. Capability parts are not extra entities.

A truck can be travelling, waiting at a dock, loading, hauling, paused or broken according to actual engine work. A refinery can be disabled or blocked even with fuel present. Hosts display those facts; they never infer “running” from stock.

Future nonspatial entities have identity, ownership and Update/state without mandatory coordinates. Spatial position and previous-position projection belong to an optional provider.

How to extend without editing the scheduler

  1. Choose the owner. A new resource definition uses the existing catalog. A specialized inventory owns its buffer once. A new worker/process/incident implements the registered capability, not a renamed duplicate system.
  2. Declare contracts. GameModule declares exact identity/version/dependencies; DeclareContent registers definition sections/components with explicit schemas. Compose registers owned services, commands, events, systems and view features.
  3. Author JSON. Add stable IDs and references under explicit master-listed documents. No file scanning, global static session state or default provider selection.
  4. Validate before Initialize. Fail duplicate/missing/incompatible declarations, invalid units, cycle edges and ambiguous owners. Freeze shared definitions and capture metadata once.
  5. Use existing execution. Requirement preview is pure. Commands revalidate at the current checkpoint. Work/process/logistics providers use real time and owned commitments.
  6. Own state and expose facts. One Sync per stateful provider supplies save/load/hash. Immutable viewer-scoped views expose progress/blockers; never expose a mutable World or provider delegate.
  7. Prove extension independence. Compile a public-contract module without friendship, then test physical work, cancellation, saved twins and no host gameplay.

Questions and explicit boundaries

Is the enhancement plan implemented?

No. The audit, stage documents, master and this help are complete. P2 is partial with a passing standalone gate; later stages remain planned. Quick setup proves only a scoped current-API smoke path.

Do we need a new ResourceManager?

Not another catalog or balance store. ResolvedContent already owns definitions. P7 exposes/extents that authority through resource contracts; actual stock stays in IInventory.

Why a TransformerManager?

It generalizes the existing production coordinator for crafting/refining/process providers. It replaces ProductionSystem and uses provider-owned state, rather than adding a duplicate tick/queue.

Does each entity get updated?

Yes. The existing World.Step reaches each live entity.Update after settled shared phases. The plan preserves that engine-owned loop and removes mandatory spatial/type assumptions.

Can I drill without seismic or logging?

Yes in the intended oil workflow. They are optional knowledge branches, not drilling requirements. P5 must prove unsurveyed legal-site preparation/drilling/completion through physical commands.

Can a host choose actions?

A human/scripted player can choose a command or strategy using engine facts. It cannot decide validity/cost/route/timing, consume stock, complete work, set entity state or simulate incidents locally.

Where are Draw and rendering?

They belong to a future game platform and are not implemented in SimEngine. Initialize and Update publish simulation data only. No Draw callback, adapters or platform SDK code is implemented here.

What happens to legacy content?

Replaced schemas/APIs/owners are removed and consumers migrate in one slice. Old saves/manifests fail explicitly. No compatibility shim, merge patch, fallback or duplicated subsystem is planned.
