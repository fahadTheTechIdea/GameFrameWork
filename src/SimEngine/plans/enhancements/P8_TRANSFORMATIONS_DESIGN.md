## Execution lifecycle and accounting

Idle → waiting requirements/supply → acquiring → running → waiting output → committing → completed.
Disabled/paused retains existing progress; cancelled/failed uses authored WIP handling.
This operation lifecycle belongs to the provider; IEntity.Update derives/commits entity state once.

- Batch input consumption moves quantities into that execution's WIP ownership once, with an atomic
  P7 resource transaction. Save WIP, selected alternatives, reservation tokens and effect commit IDs.
- Output capacity, catalysts, tools and entity placement are reserved before irreversible start when
  the recipe requires it. Authored backpressure can allow WIP accumulation with explicit capacity.
- Continuous processing derives native quantities from earned progress using cumulative ceiling
  inputs/floor products; no copied fractional remainder balance. Rate changes use current engine time/typed units.
- Utilities gate progress through provider facts; do not maintain local fake power or water totals.
- Multi-output commit succeeds together or waits intact. No partial output plus an extra vehicle,
  silent byproduct disposal, input recreation or hidden container.
- Probability/yield providers, if selected, use the world's deterministic random source and record the
  outcome once at the authored stage; previews never sample RNG. Guarantees/estimates are distinguished.
- Queue/repeat/cancel/reorder commands share the current command path and engine preview evaluator.
  Repeats allocate a new execution identity; recipe dependency cycles are not activity-DAG cycles and
