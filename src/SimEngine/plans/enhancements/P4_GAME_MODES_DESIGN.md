## Specification

A game needs an authored mode preset and independently configurable rules without making
money, income, budgets, trading, or Tycoon mandatory. Add the main configuration class
`GameModeConfiguration`, not another main game, factory, loop, scheduler, or clock.
`GameDefinition` → `GameFactory` → `SimGame.Initialize/Update` remain the existing owners.

Success means:

1. An explicitly selected survival profile defaults all monetary features off, while real
   materials, compatible workers, hauling, construction, prerequisites, and elapsed game time remain.
2. A scenario can select another profile or explicitly override allowed properties. No
   `if (mode == "survival")` gameplay branches or compiled survival/Tycoon preset enum.
3. All property definitions, defaults, profiles, and scenario overrides use master-listed JSON
   and existing contracts/content resolution. New profiles require data, not scheduler edits.
4. Every enabled setting has a responsible engine capability; disabled and unavailable are
   distinguishable. Unsupported settings refuse, rather than becoming decorative UI toggles.
5. The effective configuration is immutable, reproducible, saved, hashed, lockstep-checked,
   and readable through public engine contracts. Hosts never implement its rules.

## Ownership decisions

| Responsibility | Sole owner / planned change |
|---|---|
| Code module registration and creation | Existing `Kernel/Modules.cs:226` `GameDefinition` |
| Selected modules, scenario, time and space | Existing `ScenarioDef` and `WorldSettings`; extend in place |
| File enrollment, parsing, definitions | Existing `ContentSet`, `ContentTypes`, `ResolvedContent` |
| Property schemas and preset defaults | Proposed `GameModePropertyDef` / `GameModeDef` in that catalog |
| Effective session configuration | Proposed immutable `GameModeConfiguration : IGameModeConfiguration` |
| Optional monetary interpretation | One proposed `BusinessModeRules` contract projection over that configuration |
| Balances, monetary reservations, settlement provenance | Existing `BusinessAccounts` / `IEconomy`; no new ledger |
| Physical stock, jobs, DAGs, movement, entity states | Existing owners, unchanged by a mode label |
| Time, Initialize, Update | Existing `GameClock` and `SimGame`; no mode update loop |
| Display/input | Future platform or current thin host; no Draw in this framework |

The immutable configuration stores resolved settings, not accounts, entity states, inventories,
technology progress, objectives, resource values, utility state, or map layers. Modules consume
contracts; no system reaches into raw JSON to decide gameplay on each Update.

## Initial economics properties

USER CLARIFICATION,2026-10-07: Work, hauling, building and manufacturing are normal simulation
capabilities, never Tycoon features. Settlers-style and space-colony games run them with physical
resources/providers and time without budgets, income, markets or the business module. The properties
below gate **monetary costs/rewards only**. There is no `tycoon` prerequisite for work/manufacturing;
even opt-in monetary work costs require accounts, not advanced Tycoon activation.

Proposed stable property IDs, owned semantically by the optional business capability:

| Property | Survival preset | Meaning when enabled |
|---|---|---|
| `business.values.enabled` | false | Select authored valuation policy/catalog; does not create money |
| `business.money.enabled` | false | Create the one explicitly configured account service |
| `business.production_income.enabled` | false | Reward eligible committed production through selected income policy |
| `business.construction_costs.enabled` | false | Enforce explicitly authored monetary building/work costs |
| `business.manufacturing_costs.enabled` | false | Enforce explicitly authored process-start monetary charges |
| `business.running_costs.enabled` | false | Enforce explicitly authored monetary upkeep/running charges |
| `business.trading.enabled` | false | Allow explicitly authored monetary purchases/sales, if providers exist |
| `business.tycoon.enabled` | false | Activate explicitly selected advanced economic rule providers |

Income, construction/process/running monetary costs, trading, and Tycoon require money.
Income also requires values, an income policy, and real resource transactions. Tycoon requires
its actual advanced provider; the fixed-values provider is not an advanced substitute.
Accounts can be enabled with income and budgets off. Values can be enabled with accounts off.
No cost is invented because an account/value exists. An explicit zero price differs from no
trading capability. `business.money.enabled=false` does not mean unlimited-money dummy accounts.

Survival is a **recommended authored preset for this framework**, not a claim that every
commercial survival game disables currency. Research conclusions and boundaries are in I1.

## Other game properties

The configuration supports registered Boolean, fixed-point numeric and constrained text/identity
properties. A module can define settings for incident pressure, inspection discipline, resource
scarcity, research rules, operational damage, utility requirements or objective pacing when it
provides real engine enforcement. These are examples, not new implementations or universal defaults.
Game-specific domain settings remain engine-side extension content.

Mode presets and difficulty presets are distinct concepts: a harder survival scenario need not
enable money, and a monetized colony need not introduce trading. Initial implementation uses one
flat profile with explicit overrides; no inheritance tree, layered preset merger or expression language.
Sandbox/admin permissions stay separately explicit. A sandbox label never grants instant spawn,
free resources, ignored machine requirements, or unsafe recovery implicitly.

Existing time definitions and world-layer definitions remain authoritative. Do not add another
current time, platform size caps, renderer settings, or Godot/Unity configuration to modes.

## Acceptance and non-goals

Use the exact bounded stage scenarios in I2–I4 at completed slices, not broad filtered families or
full tests after each edit. I2 foundation ran one exact scenario99 checks after a clean final build;
one test-constructor repair required rebuilding. Existing H1's72-check
report is historical evidence for that source, not proof of the newer account2/view2/H2 edits.

No legacy loader, compatibility shim, second scenario database, mode-specific simulation engine,
new market mechanics, population, combat, platform adapter, rendering, or OilFieldDays edits.
Live session mode switching is deferred: existing obligations make it a separate deterministic
command/state-migration design, not a mutable configuration setter.

## Decisions for implementation

- Adopt one immutable configuration class attached to the existing session, exposed by contract.
- Require an explicit profile for migrated scenarios; no hidden default or old-settings inference.
- Resolve profile defaults → scenario overrides → validated new-game overrides exactly once.
- Keep modules explicitly selected by existing scenario/master content. Settings do not load code.
- Lock the configuration for the session. Save/load restores the same intent and validates identity.
- Implement generic properties only with declared type/range/ownership and real capability use.

All runtime tasks remain unchecked in the master until their exact gates are executed.
