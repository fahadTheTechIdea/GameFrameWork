## 0. Problem statement

The initial audit found frozen ScenarioDef settings without shared mode/property contracts.
The current implementation extends ScenarioDef and ContentSet.ResolveScenario in place: native
profile/property contracts, immutable resolution and captured request intent now exist. Remaining
owned-scenario migration and actual rule enforcement must use that same path, never a second main
game or JSON loader.

## 1. Goals

1. One immutable `GameModeConfiguration` is established before any composition/Initialize callback.
2. Property schemas, named presets, and overrides are explicit master-listed JSON.
3. Stable IDs and typed lookups permit data-only profiles and independently registered game rules.
4. Unknown/type-invalid/range-invalid/forbidden/conflicting overrides fail before gameplay mutation.
5. Mode resolution is identical regardless of document/property enumeration order.

## 2. Design

### One responsibility per class

Implemented engine contracts/native definitions:

- `IGameModePropertyDefinition`: identity, kind, explicit authored default, allowed range/text
  identities, override permission, capability owner and simple declared Boolean prerequisites.
- `GameModePropertyDef : Def`: native JSON definition implementing that contract.
- `IGameModeDefinition`: profile identity, immutable authored property assignments.
- `GameModeDef : Def`: native profile implementing that contract.
- `IGameModeConfiguration`: read-only resolved values/provenance for the selected session.
- `GameModeConfiguration`: sole resolution class/immutable effective configuration. Static or
  internal creation resolves typed definitions and override intent; no public mutation or Update.
- `GameModeValue`: immutable tagged Boolean/Fix/constrained text value, not arbitrary CLR objects
  or executable JSON. Wrong-kind access refuses; a default struct is not an authored false/zero.

`ResolvedContent` remains the only definition catalog. Do not add a property registry service,
mode manager, provider discovery scanner, separate scenario database or session-global singleton.
Definitions register once in existing `ContentTypes`. Modules use the read-only contract through
`World`/`WorldComposer`; `SimGame` exposes that same configuration contract to hosts.

### Explicit authoring and defaults

Native accepted schema example:

```json
{
  "game_mode_properties": [
    { "id": "business.money.enabled", "kind": "boolean", "default": false,
      "capability": "sim.tycoon", "overridable": true, "requires_when_true": [] },
    { "id": "business.production_income.enabled", "kind": "boolean", "default": false,
      "capability": "sim.tycoon", "overridable": true,
      "requires_when_true": ["business.money.enabled", "business.values.enabled"] },
    { "id": "business.values.enabled", "kind": "boolean", "default": false,
      "capability": "sim.tycoon", "overridable": true, "requires_when_true": [] }
  ],
  "game_modes": [
    { "id": "survival", "name": "Survival", "properties": {
      "business.money.enabled": false,
      "business.production_income.enabled": false,
      "business.values.enabled": false
    } },
    { "id": "valued-colony", "name": "Colony with resource values", "properties": {
      "business.money.enabled": false,
      "business.production_income.enabled": false,
      "business.values.enabled": true
    } }
  ]
}
```

The complete initial property file also defines construction/manufacturing/running monetary costs,
trading and Tycoon, each with explicit false default and prerequisites from the parent design.
Profiles are flat. Omitted profile assignments use the property's **explicit JSON default**, not
C# defaults, mode-name inference or previously saved settings. No profile inheritance or cascade.

An existing manifest entry lists these documents exactly as other content:

```json
{
  "schema": 1,
  "modules": [
    { "id": "proof.game", "version": "1.0.0", "documents": [
      "core.json", "game-mode-properties.json", "game-modes.json", "scenarios.json"
    ] }
  ]
}
```

This is a schema illustration; use actual registered module IDs/versions in implementation fixtures.
A survival profile may declare disabled optional-business properties in selected core game content
without selecting/resolving business resource-value documents or constructing accounts. The capability
identity must refer to a registered code module, but a false flag does not require it to be composed.
An enabled flag requires its selected provider during composition. Do not force all optional content
to resolve merely to discover profiles. Document/definition ownership uses existing manifest rules.

Native scenario fields:

```json
{
  "id": "survival-field",
  "game_mode": "survival",
  "mode_overrides": {},
  "time": "game.second",
  "modules": ["proof.game"],
  "seats": 1,
  "default_seats": 1
}
```

Keep existing time/space/module/settings fields authoritative. A custom monetized-survival scenario
explicitly selects `sim.tycoon`, supplies actual policy/account parameters in its existing module
settings, and overrides the desired flags. Mode properties never select code modules secretly.

### Resolution precedence and validation

1. Read selected property definitions and their explicit defaults.
2. Apply selected profile assignments.
3. Apply scenario `mode_overrides` permitted by the property definitions.
4. Apply permitted typed `NewGameRequest.ModeOverrides` as player intent, if supplied.
5. Validate the complete result before constructing providers: known IDs, kind, bounds/text domain,
   override permission, property references, and all Boolean prerequisites. Never auto-flip dependencies.
6. Freeze and publish one effective configuration in ordinal property-ID order, with provenance:
   property default, profile, scenario override, or request override.
7. Validate actual enabled capability availability at composition, then Initialize as usual.

Property constraints are comparisons over a fully resolved map, not sequential commands or another
activity DAG. Avoid a scripting/expression engine for eight enablement flags. Runtime definitions
remain extensible through existing registered Def/contracts; executable rule behavior belongs to
engine-side capability providers, never arbitrary type names or code strings in JSON.

Missing requested property is explicit unavailable/refusal, not zero/false. Numeric values use Fix
with authored bounds and existing unit definitions where relevant. Durations use existing time
definitions/contracts rather than a new numeric clock field. Profile IDs are open identities, not
an enum of known genres. New mode/property content can be listed in another master document.

## 3. API surface

Implemented read contract:

```csharp
public interface IGameModeConfiguration
{
    string ModeId { get; }
    IReadOnlyList<GameModePropertyView> Properties { get; }
    bool TryGet(Code property, out GameModeValue value);
}
```

`GameModePropertyView` contains only immutable value/definition/provenance facts. Module-specific
rule contracts perform required typed lookup once and reject missing/wrong-kind definitions.
`ScenarioInfo` gains declared mode metadata; effective preview needs full selected-module resolution,
not the raw menu-discovery parser pretending it has resolved providers.
`NewGameRequest` carries optional typed overrides; the engine captures them defensively.
Requests do not set balances, bypass requirements, or expose mutable World/configuration state.
The current public ModeOverrides list is explicitly empty by default; null refuses. Immutable
GameModeAssignment validates identity/value presence; capture ordinal-sorts and rejects duplicates.
GameFactory.PreviewGameMode uses the same resolver without composition/Initialize. WorldSettings
stores canonical request intent plus selected profile; effective values stay derived, not saved twice.

## 5. Error handling matrix

| Input | Required outcome before Initialize |
|---|---|
| Missing/unknown profile or property reference | ContentException with scenario/document/property identity |
| Duplicate IDs/JSON keys or owner declaration | Existing strict loader refusal; no last-writer-wins |
| Wrong value type/out-of-range number/unknown text identity | Typed content/request refusal |
| Override forbidden or dependent flag incoherent | Refusal explaining property and prerequisite |
| Enabled property but provider not selected | Composition refusal; never silently enable a module |
| False optional property with provider omitted | Valid disabled intent; no fabricated service |

## 8. Risks

Configuration must resolve before providers read it, without resolving unrelated optional game data.
Definition defaults are explicit content, not hidden engine defaults. Generic properties must not
become an untyped dictionary that silently accepts settings nobody implements.

## 9. Out of scope

Live changes, preset inheritance, automatic module activation, rendering, platform size constraints,
new clocks, engine-external gameplay, or implementing income/Tycoon merely because flags exist.
