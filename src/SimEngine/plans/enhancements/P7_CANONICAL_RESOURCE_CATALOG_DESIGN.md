# P7-CA1 — Canonical resource projection and wide physical stock

## 0. Problem statement

`ResolvedContent.Resources` currently builds a new GetRange/read-only collection for every call despite the catalog's frozen lifecycle. The original P7.020 ownership/no-hidden-limits/legacy gate needs current structural and runtime evidence rather than historical claims.

## 1. Goals

1. Publish one stable readonly resource collection from the original compact-ID owner, shared by IResourceCatalog.Definitions.
2. Preserve the actual definition references, assigned IDs, one resolution per definition and deterministic content fingerprint.
3. Prove257 native/independent resource kinds in one actual physical inventory, high-index hauling/manufacturing/cancellation, private views and saved continuation.
4. Refuse duplicate identities, obsolete implicit fields and checksum-valid old builds/formats without migration.

## 2. Design

`ResolvedContent` finalizes its resource collection once after all master-listed definitions collect and before cross-reference resolution. Its existing private list/ID dictionary remain the identity authority. Finalized content cannot collect another definition. No new catalog, stock balance, capacity calculation, component codec or resource scheduler is introduced.

The existing independent resource module checks all actual native/contract aliases and stable projection identity. Its original two-resource fixture defaults remain valid. The existing public physical helper accepts an expected catalog count (default2) so the new driver can author255 native entries plus the two actual independent definitions, without copying gameplay into the test.

A private native store starts with all257 kinds through original WorldSetup/initial-stock transactions and JSON capacity300. Direct.unused uses quantity2 because its authored0.5 discrete-capacity coefficient requires the original exact quantum. The actual high-index supply still moves by machine and enters original production WIP/tools.

## 3. API surface

Resources keeps its current public contract and now returns one stable readonly projection. Engine2.507.0/save154/replay1. No backwards-compatible loader or fallback field is introduced.

## 4. Files to change

Existing ResolvedContent and engine/protocol identity; existing DirectResourceContentProof and public physical helper signature; new CanonicalResourceCatalogTests; profile/registration; current tracker/evidence.

## 5. Error handling

Late collection, duplicate native/independent IDs and obsolete resource/storage fields refuse explicitly. Old build/schema refuses despite valid checksum. Authored measured capacity remains authoritative; no item-count default or silent truncation.

## 6. Compatibility

Development-only engine identity change. Legacy saves and fields stay unsupported.

## 7. Verification

One solution build and one new exact case (90seconds). Existing public helper routines may execute inside this new authored fixture; no older case/family/full registry is invoked. Source ownership audit maps canonical catalog, stock/reservations, WIP, graph inventories, optional account owner and strict loader separately. Full regression remains deferred until implementation is finished.

## 8. Risks

A stable collection is not a new definition-state owner; actual frozen definitions are shared intentionally.257 is a bounded proof fixture, not a runtime limit or infinite-memory guarantee. The gate must not be closed using only a grep or a metadata count.

## 9. Out of scope

Tycoon rules, Oil content, platform/Draw/adapters, complete transaction stress, quality/lot gameplay, and the final full-regression executor.

## 10. Execution order

1. Finalize the original collection once.
2. Extend original alias instrumentation and public helper data expectations.
3. Build and execute the new wide-stock/physical/strict-loader case.
4. Attach structural owner evidence, update original gate only if its literal scope is proved, and preserve other open gates.
