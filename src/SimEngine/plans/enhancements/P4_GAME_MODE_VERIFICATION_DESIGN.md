## 0. Problem statement

`WorldSettings.Sync` already serializes creation intent; `SaveGame` checks selected content;
`Lockstep.SameSettings` compares peer settings. New-game overrides can produce different effective
rules with identical content, so content fingerprint alone cannot establish session identity.

## 1. Goals

1. Save/load/continue recreates exactly the selected mode and allowed captured overrides.
2. Hashes and peer validation include effective mode identity, not just current account existence.
3. Public views provide detached settings/provenance with no mutable provider/account escape.
4. Two interleaved sessions sharing ContentSet can have different modes without cross-contamination.
5. An independent public proof adds a mode/property/rule provider via contracts and master JSON.

## 2. Design

### Persistence and identity

Extend existing `WorldSettings.Sync` with the selected profile identity and canonical request-override
intent. Scenario overrides and defaults remain in content, not copied into a mutable saved property
database. `GameModeConfiguration` is a derived immutable resolution of that intent plus frozen defs;
it is not an independently writable service/codec. Header mode identity must match the scenario.

Use the existing sync/hash protocol to include canonical effective mode identity at the current
session settings/core identity boundary. Ensure `World.Hash`/part diagnostics cover the same rule
identity; do not assume the save header or content fingerprint is already part of the state hash.
Peer `SameSettings` compares selected mode and canonical overrides; a same-content mismatch refuses
hello before any gameplay. Replays record the same initial settings and existing command/checkpoint
stream. No separate mode replay or serialization implementation.

Load must re-resolve/validate the profile, overrides, selected provider declarations and schemas
before initialization/gameplay effects. Disabled providers remain absent after load. Never create
accounts because a saved balance is zero or recover rules from stock/earned income.

Bump actual engine/save/protocol identity when required by changed WorldSettings payloads and migrate
owned fixtures directly. A module codec bump alone is not evidence that the session header format
remains valid. No old-save reader, compatibility alias or best-effort missing-property fallback.

### Read models and setup previews

Expose immutable `IGameModeConfiguration` from SimGame and the same read-only contract to engine
providers. `ScenarioInfo` lists authored mode metadata without resolving unrelated business data.
An engine-owned setup preview resolves selected modules/profile/request overrides and reports typed
missing capabilities/parameters before `NewGame`; hosts display it, not duplicate the validator.

Retained property collections, values and provenance cannot mutate. Numeric/text access cannot
reinterpret false/zero/null as “use default.” Public mode configuration exposes public scenario rules,
not private balances, surveyed geology, hidden activity, or mutable policy/provider objects.
Business views distinguish values-only/no-account/no-income from real zero balances/rewards.

### Public extension proof

Use existing `ExtensionProof` without InternalsVisibleTo. Add explicitly embedded JSON documents
and an engine-side module using public contracts, not a test-owned rule implementation:

1. A new profile ID not known by any framework enum.
2. A namespaced fixed-point/constrained-text property with declared schema and limits.
3. An actual engine-side rule provider whose normal operation consumes that property.
4. One physically timed public-command workflow showing changed behavior and unchanged conservation.
5. A master document addition enrolling the profile/property, with no framework scheduler modification.

Adding data alone cannot claim a new mechanic: executable behavior stays in that capability's engine
module. Save/hash/session proofs observe actual owner state, not an artificial mirror in a harness.

## 3. API surface

Extend the existing creation/menu/save metadata contracts for mode identity and typed setup diagnostics.
Reuse immutable config views and existing result/refusal conventions. No runtime mode-change command
in this stage. If later requested, outstanding jobs, money obligations, controllers and peers need
an explicit new design before such a command exists.

## 5. Error handling matrix

| Failure | Required refusal |
|---|---|
| Same content, different effective mode/overrides between peers | Deterministic settings-differ refusal before Update |
| Missing/changed mode/property definitions or provider schema | Save incompatibility/restore refusal before gameplay |
| Corrupt tagged override, duplicated ID or noncanonical identity | Corrupt state; no partly applied rules |
| Profile says income true but H2 integration unavailable | Unsupported composition, not a misleading enabled view |
| Host attempts mutation of retained views/request after capture | No session change; immutable/defensively captured data |

## 6. Compatibility

Development-only current-schema migration. No parallel mode codec, compatibility deserializer,
legacy defaults, old save upgrade path or mutable effective-state authority.

## 7. Verification

Run only the exact new affected scenario `Game modes: saved identity, lockstep and session isolation`
(proposed name) when its slice is complete. Bound physical waits by the one game clock and a diagnostic
snapshot on timeout. Cover save during material/machine/budget waits, continuation hashes, retained
views, changed overrides, peer mismatch, reverse property arrival, independent extension and interleaving.

Maintain a capability matrix, never a blanket “all modes work” claim:

| Acceptance | Required proof |
|---|---|
| Resource-only survival | No business services; positive authored monetary gates off; real supply/work/time |
| Values-only | Unit-correct quotes; no accounts/income |
| Accounts without income/budgets/trading | Actual account owner, no implicit monetary effects |
| Opted-in construction/manufacturing budgets | Existing requirement/charge timing and shortage/cancellation semantics |
| Default production income | H2 actual committed gold100000 and no transfer/replay double payout |
| Advanced Tycoon | H3 actual provider/rules, no fixed-policy substitution or extra account owner |
| Custom game mode/property | Public module/content extension with real enforcement |

The initial planning revision ran no build/tests. The subsequent I2 foundation built and ran its
one99-check configuration scenario, not this proposed I4 scenario. Build when necessary at completed
slices; do not rerun older/full/family suites without user request. Unexecuted final regression remains
open. Current H1 historical72 assertions are not evidence for changed H2 or new modes.

## 8. Risks

ContentSet caches by selected module set. Never cache effective session overrides in that shared
catalog or let one session change another's defaults. Save/lockstep/hash must validate the same captured
intent, while rendering/speed controls remain outside gameplay configuration.

## 9. Out of scope

Live switching, matchmaking policy, achievements, external telemetry, platform adapters/Draw,
automatic old-save migration or user-unrequested full regression.
